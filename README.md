# 회사 조직원 KPI 관리 대시보드

조직원의 KPI를 등록·관리하고, 관리자가 조직 전체의 진행 현황을 실시간으로
확인할 수 있는 웹 기반 대시보드. Flask 기반이며 관리자와 조직원의 권한을
분리해 서로 다른 기능을 제공한다.

---

## 1. 빠른 시작

```bash
pip install -r requirements.txt
python seed.py      # 샘플 데이터 생성 (선택)
python run.py
```

브라우저에서 <http://127.0.0.1:5000> 접속.

`seed.py` 없이 `run.py`만 실행해도 동작한다. 이 경우 테이블이 자동 생성되고
초기 관리자 계정(`admin` / `admin1234`)이 만들어진다.

### 샘플 계정

| 구분 | 아이디 | 비밀번호 |
|---|---|---|
| 관리자 | `admin` | `admin1234` |
| 조직원 | `seojun` | `test1234` |
| 조직원 | `hayoon`, `dohyun`, `siwoo`, `yerin`, `minjae`, `sua`, `jiho`, `chaewon`, `doyoon` | `test1234` |

> 운영에 쓰기 전에 관리자 비밀번호를 반드시 변경할 것.

## 2. 개발 환경

### Backend
- Python 3.x / Flask
- Flask-SQLAlchemy (ORM)
- Flask-Login (로그인 세션)
- Flask-WTF (폼 검증 + CSRF 방어)
- SQLite

### Frontend
- HTML5 / CSS3 / JavaScript
- Bootstrap 5 (CDN)
- Chart.js 4 (CDN)

### 데이터베이스 확장

`config.py`의 접속 주소는 `DATABASE_URL` 환경변수로 덮어쓸 수 있다.
PostgreSQL이나 MySQL로 옮길 때 **코드 수정 없이** 환경변수만 바꾸면 된다.

```bash
# PostgreSQL 예시
set DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/kpi
python run.py
```

   ├─ forms.py             입력 폼과 검증 규칙

   ├─ templates/
   │  ├─ base.html         공통 레이아웃 (내비게이션, 알림)
   │  ├─ _macros.html      반복되는 UI 조각 (진행바, 배지, 폼 필드)

`blueprints/` 아래에 파일 하나를 더하고 `create_app()`에 등록만 하면 된다.

## 4. 데이터 구조

```
Department (부서)  1 ──< User (조직원)  1 ──< Kpi (KPI)  1 ──< KpiUpdate (실적 입력 이력)
```

부서를 문자열이 아닌 별도 테이블로 뺀 이유는, 부서명이 바뀌어도 한 곳만
고치면 되고 부서별 집계가 정확해지기 때문이다.

### KPI 항목

요청서 6-1의 항목을 모두 구현했다.

| 항목 | 저장 방식 |
|---|---|
| KPI ID, 조직원, KPI명, 설명 | DB 컬럼 |
| 목표값, 현재값, 단위 | DB 컬럼 |
| 시작일, 종료일, 가중치 | DB 컬럼 |
| 최종 업데이트 | DB 컬럼 (수정 시 자동 갱신) |
| **진행률** | **자동 계산 (저장하지 않음)** |
| **상태** | **자동 계산 (저장하지 않음)** |

진행률과 상태를 저장하지 않는 이유: 저장해 두면 현재값만 바뀌고 진행률은
옛날 값이 남는 불일치가 생길 수 있다. 계산해서 쓰면 그런 문제가 없다.

## 5. 진행률과 상태 계산

### 진행률

```
진행률(%) = 현재 실적 ÷ 목표 실적 × 100
```

- 목표값이 0이면 나눌 수 없으므로 0%로 처리한다 (등록 시에도 0을 막는다)
- 초과 달성은 100%를 넘는 값을 그대로 보여준다 (예: 115%).
  단, 막대그래프 너비만 100%에서 자른다

### 상태 자동 판정

요청서 6-1에 상태 4종(진행중/달성/지연/미달)만 명시되어 있고 판정 규칙은
지시서가 7절에서 끊겨 전달되지 않았다. 아래 규칙으로 구현했으니 회사 기준과
다르면 `app/models.py`의 `Kpi.status`만 고치면 된다.

위에서부터 차례로 판정한다.

| 순서 | 조건 | 상태 |
|---|---|---|
| 1 | 진행률 100% 이상 | **달성** |
| 2 | 종료일이 지났는데 100% 미만 | **미달** |
| 3 | 기대 진행률보다 10%p 넘게 뒤처짐 | **지연** |
| 4 | 그 외 | **진행중** |

**기대 진행률**은 전체 기간 중 오늘까지 흘러간 비율이다. 1월 1일~12월 31일
KPI를 6월 30일에 보면 약 50%다. 이 값과 실제 진행률을 비교해 "기간은 절반이
지났는데 실적은 10%뿐" 인 상황을 지연으로 잡아낸다.

3번의 10%p는 약간의 들쭉날쭉함까지 지연으로 보지 않기 위한 여유값이다.

상세 화면에서는 기대 진행률을 함께 보여주어, 담당자가 왜 '지연'인지
납득할 수 있게 했다.

### 조직·부서·개인 진행률 (가중 평균)

```
평균 진행률 = Σ(진행률 × 가중치) ÷ Σ(가중치)
```

단순 평균이 아닌 가중 평균을 쓰는 이유는 KPI마다 중요도가 다르기 때문이다.
이때 개별 진행률은 100%로 잘라서 계산한다. 한 KPI를 300% 달성했다고 해서
다른 미달 KPI가 가려지면 안 되기 때문이다.

## 6. 권한별 기능

### 관리자

| 기능 | 경로 |
|---|---|
| 실시간 대시보드 | `/admin/dashboard` |
| 조직원 등록/수정/삭제 | `/admin/users` |
| 부서 관리 | `/admin/departments` |
| KPI 등록/수정/삭제 | `/admin/kpis` |
| KPI 상세 + 실적 대리 입력 | `/admin/kpis/<id>` |
| 부서별 현황 | `/admin/departments/stats` |
| 조직원별 현황 | `/admin/members/stats` |

### 조직원

| 기능 | 경로 |
|---|---|
| 본인 KPI 목록 | `/my/kpi` |
| KPI 상세 + 실적 입력 | `/my/kpi/<id>` |
| 업데이트 이력 | `/my/history` |
| 본인 정보 | `/my/profile` |

로그인하면 권한에 따라 자동으로 갈린다. 관리자는 대시보드로, 조직원은
본인 KPI 화면으로 이동한다.

## 7. 권한 분리를 지키는 방법

요청서 3-2의 **"조직원은 다른 조직원의 KPI 정보를 조회하거나 수정할 수 없어야
한다"** 는 화면에 링크를 그리지 않는 것만으로는 전혀 지켜지지 않는다.
주소창에 남의 KPI 번호를 직접 입력하면 그만이기 때문이다.

그래서 서버에서 세 겹으로 막는다.

1. **관리자 화면 전체 차단** — `blueprints/admin.py`의 `before_request`가
   이 파일의 모든 라우트를 한 번에 막는다. 라우트마다 데코레이터를 붙이는
   방식은 새 기능을 추가할 때 빠뜨리기 쉽다.

2. **소유자 확인** — 조직원이 KPI를 꺼내는 모든 지점에서
   `utils.get_owned_kpi_or_404()`를 거친다. 확인 로직이 한 곳에만 있어
   빠뜨릴 수가 없다.

3. **404로 응답** — 403이 아니라 404를 준다. 403을 주면 "그 번호의 KPI는
   존재한다"는 사실이 드러난다. 없는 것처럼 보이게 하는 편이 안전하다.

같은 이유로 로그인 실패 문구도 아이디가 없을 때와 비밀번호가 틀렸을 때를
하나로 통일했다. 문구를 나누면 유효한 아이디 목록을 만들 수 있게 된다.

### 그 밖의 보호 장치

- 비밀번호는 해시(scrypt)로만 저장한다. 평문은 어디에도 남기지 않는다
- 모든 폼에 CSRF 토큰이 들어간다 (Flask-WTF)
- 삭제는 GET이 아닌 POST로만 처리한다
- 비활성 계정은 로그인할 수 없다
- 마지막 관리자는 삭제·비활성화·권한변경을 할 수 없다
  (아무도 시스템에 들어갈 수 없게 되는 상황을 막는다)
- 소속 조직원이 있는 부서는 삭제되지 않는다
- 로그인 후 이동할 `next` 주소는 내부 경로만 허용한다 (오픈 리다이렉트 방지)

## 8. 실시간 대시보드

`static/js/dashboard.js`가 30초마다 `/admin/api/chart-data`에서 JSON을 받아
차트와 요약 숫자만 갈아 끼운다. 페이지 전체를 새로고침하지 않으므로 화면이
깜빡이지 않고 스크롤 위치도 유지된다.

집계는 모두 서버(`utils.py`)에서 한다. 가중 평균 같은 규칙이 화면과 서버에
따로 있으면 두 숫자가 어긋나기 때문이다.

차트 3종:
- 부서별 평균 진행률 (가로 막대)
- KPI 상태 분포 (도넛)
- 진행률 하위 조직원 10명 (가로 막대) — 관리자가 먼저 봐야 할 대상 순서

## 9. 반응형

PC와 태블릿에서 쓸 수 있도록 Bootstrap 5의 그리드를 사용했다.

- 좁은 화면에서는 상단 메뉴가 햄버거 버튼으로 접힌다
- 모든 표는 `table-responsive`로 감싸 가로 스크롤이 생긴다
- 카드는 화면 폭에 따라 1~4열로 자동 배치된다
- 태블릿 세로(768px)에서 가로 스크롤 없이 표시되는 것을 확인했다
- 현황 화면을 인쇄하면 메뉴와 버튼은 빠지고 표만 출력된다

## 10. 기능 점검

```bash
python smoke_test.py
```

55개 항목을 확인한다. 로그인·권한 분기, 관리자 화면 접근, 조직원의 관리자
화면 차단, **조직원 간 KPI 격리**, 실적 입력과 이력 기록, CRUD, 중복 검사,

> 스스로 정리한다. 실행 전 `python seed.py`가 필요하다.

## 11. 확장할 때 참고할 점

- **KPI가 수만 건을 넘어가면** `blueprints/admin.py`의 KPI 목록 필터를
  손봐야 한다. 지금은 상태가 계산값이라 파이썬에서 거르는데, 그 규모에서는
  상태를 컬럼으로 저장하고 DB에서 거르는 편이 빠르다.
- **여러 명이 동시에 쓰는 환경**이라면 `run.py`의 개발 서버 대신
  gunicorn 등 WSGI 서버를 써야 한다.
- **KPI 기간이 연 단위로 반복된다면** 연도(분기) 개념을 담는 테이블을
  추가하는 것이 자연스럽다.
